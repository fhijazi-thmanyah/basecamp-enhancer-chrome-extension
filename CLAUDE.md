# CLAUDE.md — basecamp-enhancer

MV3 Chrome extension scoped to Basecamp. Six features, all idempotent, continuous, and individually toggleable. See @README.md for install/usage.

**Publish gate — the Claude Code launcher is gated by POSTHOG FEATURE FLAGS (v1.19.0; ONE branch, `master`).** It's a personal feature (needs the local backend), invisible to everyone whose flags resolve false: no button on the page **and** the popup hides its toggle row (`#ccRow`). Two flags in PostHog project 540812, each targeting allowed emails at 100% (currently only faris.hijazi@thmanyah.com): **`cc-launcher`** (id 797772, the launcher itself) and **`cc-hq-link`** (id 797778, the per-row "HQ ↗" tray deep links to `http://127.0.0.1:8377/#w-<session>`). content.js resolves them in `phApply` via `posthog.onFeatureFlags` (+ `isFeatureEnabled(..., {send_event:false})`) into the `ccFlags` object, caches to `chrome.storage.local.bceCcFlags` (instant on next load; also how popup.js decides `#ccRow` visibility — the popup never loads flags), and `reconcile()`s on change. Flag delivery rides the telemetry SDK: telemetry toggled off ⇒ flags stop refreshing and the cached value persists. The old compile-time `CC_ENABLED`/`CC_HQ_LINK` consts and the **`cc-launcher` branch are RETIRED** (merged/deleted 2026-08-04) — do not recreate them; to grant someone the launcher, add their email to the flags in PostHog. The manifest's `127.0.0.1:8377` host-permission, `web_accessible_resources`, and `background.js` stay in the published build (a manifest can't be flag-stripped); they're inert while the flag is off (distribution is Unlisted, so the localhost permission is harmless).

## Architecture

Content script (`content.js`, one IIFE) + background service worker (`background.js`, HQ calls only) + toolbar popup (`popup.html`/`popup.js`). No build step, no dependencies.

**Settings flow (narrow waist = `chrome.storage.sync`):** popup is dumb — it reads/writes the six feature booleans (`timeLabels`, `rtl`, `inlineReactions`, `inlineMenus`, `ccLaunch`, `telemetry`), the `bcFont` picker string, the `reactionEmojis` array, and `menuItems` (ordered `{key,label,on}` list; the popup's drag-to-reorder editor under the Inline-menu toggle — keep `DEFAULT_MENU_ITEMS` in sync across both files). The content script holds the live `settings` object, seeds it from storage on load, and listens on `chrome.storage.onChanged` to apply/revert **without a reload**. `reconcile()` is the single function that makes the page match settings (`decorateAllTimes`/`removeTimeLabels`, `applyAutoDir`/`removeAutoDir`, `applyInlineReactions`/`removeReactionBars`, `applyHoverBars`/`removeHoverBars`+`removeHoverMenus`). All off ⇒ fully reverted ⇒ plain Basecamp. Adding a feature = add its key to `DEFAULTS` (both files), a toggle row in `popup.html`, and an apply+remove pair wired into `reconcile()`/`enhance()`.

**`inlineReactions` + `inlineMenus` both feed one hover bar.** On **records** (chat lines/pings + comments, `RECORD_SEL`) the reactions and the "…" menu render together in a single floating `.bce-hoverbar` (Google-Chat–style, revealed on hover). The two toggles independently populate/strip their half of that shared pill; `applyInlineReactions` handles reactions only on **standalone** boost bars (main card/message/todo detail — a `.boosts` **not** inside a record).

- **`decorateTime` / `decorateAllTimes`** — append a `.bce-ago` span with `Intl.RelativeTimeFormat` output (`numeric: "always"` → "N units ago", never the word "yesterday"). Idempotent: reuses the existing `:scope > .bce-ago` child instead of appending a new one. Two skip rules: (1) the whole ±1-calendar-day range (`calendarDayDiff`) — Basecamp shows yesterday/today/tomorrow as a relative *word*, so a badge is redundant; (2) any `<time>` with a later sibling `<time>` (`hasLaterTimeSibling`). Basecamp emits **two** `<time>` per timestamp sharing one `datetime` (`<a>` wraps `<time data-local="weekday">Tuesday</time>` + `<time data-local="time-or-date">Jun 2</time>`); rule 2 badges only the **last** sibling so the label never appears twice (`Tuesday` stays plain, `Jun 2 (6 days ago)` gets the badge). `decorateAllTimes` handles both descendant `<time>` (via `querySelectorAll`) **and** a root node that *is* a `<time>` (the observer hands these directly — `querySelectorAll` would miss them).
- **`applyFont` / `removeFont` (font picker, v1.15.0)** — `settings.bcFont` ∈ `"" | plex | sans | seriftext | serifdisplay` (popup `<select>`, default `plex`); `applyFont` sets `data-bce-font="<choice>"` on `<html>` and `styles.css` maps each value to a family via `--bce-font`, consumed by one `!important` override rule that skips `code/pre/kbd/samp` (and their descendants). Families bundled as woff2 in `fonts/`: **IBM Plex Sans Arabic** (`plex`, 5 weights, from google/fonts, OFL — its `OFL.txt` ships too) + the three **ThmanyahFont-repo** brand families (`Thmanyah Sans`/`Serif Text`/`Serif Display`, Regular/Medium/Bold weight-ranged 300–400/500–600/700–900, converted from the private repo's OTFs via fonttools). **The default is `plex` because "the Thmanyah font" = what thmanyah.com renders** (verified live via computed styles; the calligraphic ثمانية wordmark is logo lettering, not a text face — v1.14.0 shipped repo `thmanyah sans` as the only font and the user immediately flagged it as "not the Thmanyah font"). Font URLs use Chrome's `__MSG_@@extension_id__` substitution (works in content-script CSS); the **page** origin fetches them, so `fonts/*.woff2` must stay in `web_accessible_resources`. Faces download lazily — only the selected family is ever fetched.
- **`applyAutoDir` / `setAutoDir` ("Force RTL", v1.16.0)** — `dir="auto"` resolves from the **first strong character**, so a majority-Arabic paragraph that starts with an English word/number lays out LTR (the reported bug). Rendered content is therefore decided by **majority count** (`majorityDir`: Arabic > Latin letters ⇒ `dir="rtl"`, Latin > Arabic ⇒ `dir="auto"`, and **neutral-only/tied blocks — "…", bare numbers/checkboxes — inherit the container's decision** (v1.16.2: with zero strong chars `dir=auto` defaults to LTR, which left-aligned "…" placeholder blocks in Arabic docs)), applied to each `RTL_SELECTORS` container **and** its `RTL_BLOCK_SEL` blocks (`p/li/ul/ol/h*/blockquote` + any `[dir=auto]` — the lexxy composer writes `<p dir="auto">` per paragraph, each resolving alone, which is why per-block treatment is required). Editable fields (`textarea`, `input[type=text|search]`, `[contenteditable]`, `trix-editor`) always get plain `dir="auto"` so direction follows typing. `setDir` only ever touches elements with **no** `dir` or `dir="auto"` (never an explicit `ltr`/`rtl` Basecamp set), and tags `data-bce-dir` with the **original value** (`"none"` = had no attribute) so `removeAutoDir` restores exactly. **Blockquote double-bar (v1.16.1)**: Basecamp draws the markdown-quote bar with physical `border-left` and its RTL rule *adds* `border-right` without clearing the left — any blockquote inside an RTL container shows two bars (pre-existing Basecamp bug our forcing surfaced). `styles.css` clears `border-left` under `[data-bce-dir][dir="rtl"]` so only the right bar shows; scoped to our tag so feature-off reverts.
- **Reactions (`buildReactionBar`/`setReactionBar`/`injectReactionBar`/`sendBoost`)** — Basecamp calls reactions **boosts**. Every reactable item (card, comment, message, chat line, ping) renders a uniform `.boosts` container holding a `.boosts__new-boost` "+" link whose href is `/<acct>/buckets/<bucket>/boosts/new?boost[boostable_gid]=<base64 gid>`. That single anchor is the narrow waist: `boostTarget()` derives the create endpoint (same path minus `/new`) and base64-decodes the gid from it. `buildReactionBar` makes a `.bce-reactions` span of `<button.bce-react-btn>` (one per `settings.reactionEmojis`), tagged with a `data-sig` of the emoji set; `setReactionBar(parent, lead)` adds/refreshes it as a direct child (rebuilds only when the sig changes). It lands in **two** places: `injectReactionBar` puts it in **standalone** `.boosts` (main card/message/todo detail — those **not** inside a `RECORD_SEL`, since records get reactions in the hover bar), and `applyHoverBars` leads each record's hover pill with it. Clicks go through **one delegated, capturing** document listener (survives Basecamp cloning; intercepts before Basecamp); it resolves the `.boosts` via the record (`btn.closest("[data-bce-rec]")` → `.querySelector(".boosts")`) for hover-bar buttons, else `btn.closest(".boosts")`. `sendBoost` POSTs `authenticity_token` (from `meta[name=csrf-token]`) + `boost[boostable_gid]` + `boost[content]=<emoji>` with `Accept: text/vnd.turbo-stream.html, text/html`; `applyBoostResponse` applies the reply so the reaction shows without reload, leaving the sibling `.bce-reactions` bar untouched (it's a child of `.boosts`, not of the frame).
- **Emoji order = the popup, period (no MRU).** `reactionEmojis` is a plain, fixed, user-ordered list — the bar renders it exactly as stored, newest reactions do **not** reorder it (the old recently-used rotation was removed in v1.12.8 by user request: they want a stable, manually-arranged set). The popup's emoji editor is the *only* writer, parsing input via `Intl.Segmenter` (grapheme) so packed/spaced/ZWJ emoji all split correctly; `onChanged` rebuilds every bar in that order. So `sendBoost` no longer promotes anything, there is no `recordEmojiUse`/`boostEmoji`/`captureRecentBoosts`/`captureReadyAt`, and the observer no longer scans native boosts. (`meId()` survives — it's still used for chat `data-mine`.)
- **Hover bar (`applyHoverBars`/`hoverBarFor`/`fillHoverMenu`)** — a **Google-Chat–style pill** floated at each record's **top-right on hover**, holding the quick-react emoji plus the *whole* "…" menu (Edit/Reply/Bookmark/Bubble up/Copy link/Delete/Notified…/Put in the trash), no kebab click. Records = `RECORD_SEL` (**chat lines/pings** `turbo-frame.chat-line` + **comments** on cards/todos/messages `article.thread-entry.recording`). `hoverBarFor(rec)` appends one `.bce-hoverbar` **into the record's anchor** — `.chat-line__bubble` for chat, the record itself for comments; the anchor gets `.bce-anchor` (`position:relative`) and the whole record gets `data-bce-rec` (the hover trigger). Chat bars are tagged `data-mine` (`data-creator-id` vs `me`) which CSS uses to sit them **above the bubble, matching its width** (wrapping) — so a sent bar aligns over its right-side bubble and a received bar over its left-side bubble, neither able to overflow the screen. Comments (no `data-mine`) get a compact **top-right pill**. The menu is **lazily loaded** from the record's `/…/options` endpoint; its URL + turbo-frame id differ per record (`menuSource`): comments expose it as a `turbo-frame.action-sheet__lazy-options[src]`, chat lines as the kebab toggle's `href`. `fillHoverMenu` fetches it (with a `Turbo-Frame: <fid>` header → light ~5–12 KB response, not the ~56 KB full page), finds the items (`menuRoot`: chat nests them in `.action-sheet--for-chat-line .action-sheet__content`, comments put them straight in the frame), **moves the item nodes** into a `.bce-menu` span (appended after the reactions) — dropping `.chat-line-reactions`, `.action-sheet__divider`, and mobile-only `.app-ios__show`/`.app-android__show` dupes — and strips popup-positioning target attrs. **Basecamp's Stimulus reconnects the moved controllers**: chat-room actions (Edit/Reply/Delete via `chat--room#…`) resolve against the live room ancestor; self-contained ones (`copy-to-clipboard`, `bookmarks`, nested Bubble-up sheet) ride along. Loading is lazy via one `IntersectionObserver` (`rootMargin:300px`), once per record (`.bce-hoverbar[data-menu]` guard). No ownership/left-right logic — always top-right; others' menus simply omit Edit/Delete (server-side). CSS flattens the collapsed popup into an inline strip; because the pill is **absolutely positioned and floats**, it never disturbs Basecamp's layout — no overflow to juggle (the old `:has()` footer hacks are gone). Reactions vs menu are gated **independently** by `inlineReactions`/`inlineMenus` (`removeHoverMenus` strips just the menu half; `removeHoverBars` drops the whole pill + `.bce-anchor`).
- **Claude Code launcher (`applyCcLaunchers`/`ccPanes`/`ccBuildPopover`/`ccPrompt`/`ccConfirmLaunch` + `background.js`)** — one `.bce-cc-btn` (the bundled `icons/claudecode.png`, exposed via `web_accessible_resources` + `chrome.runtime.getURL`) **per open conversation pane**, not scrolling with the convo: `ccPanes()` = every `.chat__lines` scroller's parent (`mode:"pane"` — covers the full-page room and each sidebar ping window) plus `main` when it isn't a chat (`mode:"main"` — window-scrolled, so the button is `position:fixed` bottom-left, full-size). **Pane placement = last icon in the composer's tool row**: the button mounts into `.chat__footer .chat__tools` (the emoji/attach/mic/format row) as a plain inline 26px icon — collision-proof in **both** the sidebar ping and the **maximized room**, where `.chat__tools` floats over the input's right edge so an absolutely-positioned button overlapped the format ("A") button. Fallbacks: the input's `.relative` gutter (`.bce-cc-beside` shrinks the input) if there's no tool row, then the pane host bottom-left. **Main-view button** (`data-mode="main"`): a bookmark-style tab in the pane's **left gutter**, pinned **low — ~25% up from the bottom** of the viewport (near the hand, out of the title; v1.12.5, was a top-clamp). `position:fixed` with `left`/`top` set by **`ccPositionMain`**: `left = max(6, mainLeft − 46)` (pane gutter), `top = round(innerHeight × 0.75)`. Viewport-fixed, so it's always visible without tracking the scroll — only a `resize` listener recomputes (the vertical is viewport-relative; the horizontal only shifts on resize). Uses `fixed`+JS, **not `position:sticky`** — sticky silently fails to *paint* inside Basecamp's scroll container (an ancestor with `overflow`/`contain` in the chain; verified live, layout was correct but nothing rendered). **Busy spin**: `ccSyncBusy()` (10 s interval started in `applyCcLaunchers`, cleared in `removeCcLaunchers`) matches tracked `ccSessions` to buttons by `data-url` and sets `data-busy` when that convo's worker status is `working` — CSS rotates the icon (`bce-spin`). HQ's `working` is trustworthy since 2026-07-30: the pane classifier alone read long tool runs as idle (the spinner scrolls out of the capture window — this was the "stops spinning while it's clearly working" bug), so HQ now upgrades idle/unknown → working while the worker's session **jsonl was appended < 60 s ago**, and `/api/workers` exposes `jsonl_age_s`/`claude_session_id`/`workdir`. **Click-outside closes the popover**: one capturing `pointerdown` listener (ignores clicks on `.bce-cc-btn`, which toggles itself). The tray's ✕ **kills the worker** (`hqKill` → HQ `{action:"kill"}`) then removes it from the list — except when HQ is unreachable, where the row is kept and flagged (the worker may still be running). Each button carries `data-url` from `ccPaneUrl()` (closest `turbo-frame[src]` → pane header `/circles/`-or-`/chats/` link → `location.href`), so a sidebar ping and the main card launch **independently**. Click toggles the popover (`#bce-cc-pop`, anchored above the clicked button): prompt textarea (**Enter launches, Shift+Enter = newline, Esc closes**) + "Watch ⏱️" loop segmented control (`CC_LOOPS`: oneshot/15min/60min, **default oneshot** — v1.15.0, was 15min) + a **"Reply when done"** checkbox (**checked by default**, v1.15.0) + a **"Mention that this is an automated message"** checkbox (**checked by default**, v1.15.1) + Launch + status + a persisted tray of the sessions launched on **this conversation only** (`chrome.storage.local.ccSessions` stores all, cap 10; `renderTray` filters by the popover's URL via `sameConvo`, whose `convoKey` (v1.16.7) reduces any URL to `origin + /circles/<id>|/chats/<id>` when the path has such a tail (else the path with `/my/sidebar/` stripped), after dropping `#fragment`, `?query`, and Basecamp's trailing `@<message-id>` last-read marker — the SAME ping is `/my/sidebar/circles/<id>` in the side panel, `/<acct>/circles/<id>` maximized, and picks up a fresh `@<msgid>` every visit (v1.16.5 stripped only the marker, so maximized-vs-sidebar still showed different trays; a campfire's `/buckets/<b>/chats/<id>` vs sidebar `/chats/<id>` needs the tail-match); `ccSyncBusy` uses the same matcher; live status dots polled every 5 s). Each tray row's **session name becomes a hyperlink to the session in claude.ai** once HQ reports `web_url` (plain text until then; the URL is persisted into `ccSessions` on first sight, so reopened trays link even while HQ is down), plus — only when the `cc-hq-link` flag is on (see publish gate) — a per-row **"HQ ↗"** deep link to that session in the HQ dashboard (`http://127.0.0.1:8377/#w-<session>` — HQ's `WorkerCard` carries `id="w-<session>"` and scrolls-to+flashes it on that hash). **No general "Open HQ" link** — explicitly unwanted (v1.15.0); per-session deep links only. HQ side lives in `career-coach/hq/static/app.js`: HQ spawns workers with `--session-id <uuid>` (jsonl path known from birth) + `--remote-control <tmux-name>` (never bare — its optional `[name]` would swallow the next token), and `workers._web_url` reads the jsonl's last `bridgeSessionId` (`cse_<token>` → `https://claude.ai/code/session_<token>`; appears seconds after launch). **The spawner core is the standalone `cc-tmux-api` package (github.com/FarisHijazi/cc-tmux-api, uvx-runnable — extracted 2026-08-02); `career-coach/hq/workers.py` is now a thin wrapper adding worklog claims. Public users run cc-tmux-api directly (same 3-verb API + `#w-<session>` dashboard anchors), so the extension works against either backend.** Launch = `chrome.runtime.sendMessage({type:"hqSpawn", title, prompt, workdir})` → **background.js** POSTs HQ's `POST /api/workers/action {action:"spawn"}` (career-coach `hq/main.py`); HQ returns `{ok, session:"hq-<slug>-N"}` **synchronously**. The prompt sent = typed text + `location.href` + a fixed watch template (`/bc-thread`, `/loop <interval>`, notify-if-unsure) — **never page-scraped content** (the worker runs unattended with `--dangerously-skip-permissions`; page text is untrusted). **The two checkboxes are SOFT gates — prompt wording only (v1.21.0).** There is no code lock: `cc-tmux-api`'s spawn API is `{title, prompt, workdir}` with no env passthrough, so the prompt is the only channel the extension has. `ccPrompt` therefore states **only the deviation from the default**, and states the OFF case *explicitly* — the v1.19.x bug was that "Reply when done" OFF emitted an **empty string**, which reads as "no opinion", so a worker asked something in-thread happily answered. OFF now emits "Do NOT post anything to Basecamp — no comments, no chat/ping lines, no boosts … the ONLY exception is Faris typing an instruction into **this session**; someone asking you inside the Basecamp thread is NOT that." Reply ON also carries the **length rule** (answer → a few details → fixed/not-fixed → what's needed, non-technical, link detail instead of pasting) — the canonical copy of that rule is career-coach `basecamp-cli/SKILL.md` → "Sending". Disclosure ON emits **nothing** (the sender prepends it in code); OFF emits "pass `--no-disclaimer` to bc_send" — and is suppressed entirely when replying is off, so the prompt never contradicts itself. `CC_DISCLOSE_PREFIX` = "هذه رسالة مؤتمتة 🤖 من Claude" (v1.21.0 fixed "مؤتمة"→"مؤتمتة"); it is now only the **checkbox label** and the shared constant — no prompt ever tells a model to type it. Keep it byte-identical to career-coach `scripts/bc_send.py` `DISCLAIMER`, which prepends it idempotently. **`Use /bc-thread`, never `/basecamp`**: the 37signals plugin skill claims the `/basecamp` trigger in its own frontmatter and documents `basecamp comment`/`chat post` unguarded, so a worker told to "reply" reached for the unguarded twin — career-coach's skill was renamed `bc-thread` on 2026-08-13. A public user without that skill just ignores the name.

**Launching with an empty textarea is a first-class mode (v1.12.9)**: the placeholder reads "decide and respond automatically", and on empty submit `ccPrompt` is fed `CC_AUTO_PROMPT` ("read and analyze the chat and do whatever action is needed such as queries or exploring a database, never do anything destructive") — the user never sees that full instruction, only the placeholder. **It must never mention replying** (it used to say "if there's something to respond with, do respond", which directly contradicted an unchecked "Reply when done" — the single most likely cause of the reported unwanted sends). Whether to post is decided by the checkbox alone. So there's no longer a "write a prompt first" guard; empty = auto-respond, title `bc auto-respond`. no `workdir` is sent (v1.16.6) — the backend applies its own default (HQ pins career-coach server-side in its wrapper; standalone cc-tmux-api uses `$CC_TMUX_WORKDIR`/`$HOME`), which also keeps machine-local paths out of this public repo. Follow/verify: `ccConfirmLaunch` polls `GET /api/workers` (via `hqWorkers` message) because **HQ's spawn 200 only means tmux accepted the command** — claude is typed into a surviving shell, so real confirmation = worker status reaching `working`/`waiting`/`idle` (idle counts: a fast worker can finish before the first poll); `done` after an 8 s grace (pane back at bare shell) or a vanished session = failed, and the pane `tail` is shown inline. A spawn failure whose error matches `/unreachable/i` appends `CC_SETUP_HINT` (the `mkdir -p $BCE_WORKSPACE_DIR/workspace` + `uvx git+…` start command; keep in sync with README → "Backend setup", which also covers defaulting remote control on via `/config`) so first-run users see how to start the backend — and since v1.16.4 the popover shows the same hint **proactively on open**: `pollTray` (which now always pings `hqWorkers`, rows or not) sets a `setup`-kind status when the backend is unreachable, self-clearing once it comes up and never clobbering an in-flight launch status. **Reboot survival is HQ-side (implemented 2026-07-30)**: task spawns register `$BCE_WORKSPACE_DIR/workspace/<sid>/meta.json` (`BCE_WORKSPACE_DIR` = base dir, default `~/.basecamp-enhancer`), the worker tombstones itself with `.done` when finished (✕/kill also tombstones), and HQ startup revives non-tombstoned sessions < 5 days old via `claude --resume` under the **same tmux name → same claude.ai URL → the tray rows just reconnect**; loop watchers get a `"continue"` typed in so the watch actually resumes. - **Telemetry (`phApply`/`phIdentity`/`tele` + `vendor/posthog.js`, v1.17.0, `posthog-telemetry` branch)** — PostHog usage/error analytics, identified by the signed-in Basecamp user so errors say WHO/WHERE. The real posthog-js SDK is **bundled** at `vendor/posthog.js` — the **`array.full.no-external.js`** build (every lazy dependency inlined; MV3 forbids remote-loaded code, and this build never touches a CDN) — listed **before** `content.js` in the manifest so `posthog` is a global in our isolated world; `popup.html` loads the same file for popup events. **Two gates**: the popup's "Usage analytics" toggle (`settings.telemetry`, default on; `phApply()` runs on storage-resolve + every `onChanged` and opts the SDK in/out live — the `has_opted_out_capturing()` guard matters, an unconditional `opt_in_capturing()` fires its own event each call) and `PH_KEY` (**empty = the SDK never initializes** — paste the `phc_…` project key into BOTH content.js and popup.js copies to enable; those keys are client-side/publishable). Init config (v1.18.0 "capture everything"): `persistence:"localStorage"`, `capture_pageview:"history_change"` (initial + Turbo pushState navigations = page visits for free), `autocapture:true`, `capture_dead_clicks`/`capture_heatmaps`, `disable_session_recording:false`, and remote config **enabled** — v1.17.x shipped `advanced_disable_decide`+`advanced_disable_feature_flags` for the "opted-out ⇒ zero requests" property, but that silently disabled autocapture AND replay (both wait for remote config before activating; verified: zero `$autocapture` events despite `autocapture:true`). Opted-out now still means no events/recording, just a config fetch. The replay/heatmaps/web-vitals/console-log switches are **project-side** (PostHog project 540812 settings, flipped on 2026-08-04 via MCP; `recording_domains` limited to app./3.basecamp.com; the popup keeps its own init minimal — no autocapture/recording/remote-config, custom events only). Identity: `phIdentity()` reads `meta[current-person-id]`, fetches the user's own `/my/profile` page ONCE (same-origin) to regex out email+name, caches as `chrome.storage.local.bceWho`, then `posthog.identify(email || "bc:"+id)`. Custom events via `tele(event, props)`: `reaction_sent` (ok/status/emoji), `cc_launch`/`cc_launch_result`, `extension_error` from window `error`/`unhandledrejection` listeners **filtered to stacks containing our `chrome-extension://` URL** (Basecamp's own errors never report) + sendBoost's catch, and `setting_changed` (**sent by popup.js, the single settings writer — capturing in content.js's `onChanged` would fire once per open tab**; arrays reported as counts only). PostHog's capture endpoint returns 200 even for a bad key (silent drop) — verify events in the PostHog UI, not from responses. When updating the vendored SDK: `curl -sL -o vendor/posthog.js https://unpkg.com/posthog-js/dist/array.full.no-external.js`.
- **`enhance(root)`** — runs the **enabled** features on a subtree; bails early if `root` is one of our own `.bce-ago` badges to avoid observer-feedback rework (re-enhancing a `.bce-reactions` bar is a harmless no-op). The FAB is global, so it's wired in `reconcile()` only (Turbo body swaps drop it; the `turbo:*` → reconcile listeners restore it).
- **Wiring** — `run_at: document_start`, immediate `enhance()` (uses `DEFAULTS` until storage resolves, then `reconcile()` corrects), a `MutationObserver` on `document.documentElement` (continuous), **`turbo:load`/`turbo:render`/`turbo:frame-render`/`turbo:before-stream-render` listeners that rAF-coalesce a `reconcile()`** (see flicker gotcha), `DOMContentLoaded`/`load` full sweeps, and a 60 s interval (guarded by `settings.timeLabels`) to refresh relative labels.
- **The observer watches TEXT too, and flushes per frame (v1.21.0)** — it observes `{childList, subtree, characterData}` and funnels every mutation through `markDirty` → a `Set` of dirty roots → `flushDirty` on the next `requestAnimationFrame`. Three things this fixed, all reported as "RTL/date labels don't always work": (1) **in-place text changes** (Turbo morphs, edits) fire only `characterData`/text-node swaps, so nothing was re-decided — a `<time>`'s re-rendered text kept a stale badge and an edited message kept its old direction; (2) a node added **inside** an already-decided container (a `<p>` streamed into an existing `.formatted_content`) matches no `RTL_SELECTOR` itself and got **no `dir` at all** — hence `reDirContext(el)`, which re-runs `setAutoDir` on `el.closest(RTL_SELECTORS)` (direction is a majority vote over the whole container, so any inner change invalidates it); (3) text nodes were skipped entirely. Batching is what keeps this from costing more than the old code: `enhance()` used to run **per added node** (including a full-document `[data-bce-rec]` sweep and `applyCcLaunchers`'s `getBoundingClientRect`), now it's `enhanceSubtree` per dirty root + **one** `applyCcLaunchers` per flush; >`DIRTY_MAX` (200) roots collapses to a single whole-document sweep. **The flush arms a rAF *and* a 250 ms `setTimeout` — rAF alone is a bug, because it never fires in a BACKGROUND TAB** (the first cut queued mutations forever in a hidden tab and only caught up on tab switch; verified by loading the real content.js in a hidden test tab). **`OURS_SEL` (`.bce-ago,.bce-reactions,.bce-hoverbar,.bce-cc-btn,.bce-ccpop`) is the anti-feedback guard** — mutations inside our own DOM are dropped in `markDirty`, which matters because *our own writes dominate the mutation stream* (measured: 41/41 mutations in 26 idle seconds were the 60 s label refresh writing `badge.textContent`). `.bce-anchor` is deliberately NOT in `OURS_SEL` — it sits on Basecamp's own bubble, whose contents must still be enhanced. `teardown()` cancels the pending rAF.

- **`hidden` loses to `display:flex` — `[hidden]{display:none!important}` is load-bearing (fixed 2026-08-18).** `#ccRow` is hidden via the HTML attribute when the `cc-launcher` flag is off, but `.row { display: flex }` on the same element overrides the UA sheet's `[hidden]{display:none}` — so from v1.19.0 until now **every published install showed a "Claude Code launcher" toggle** the flag was supposed to hide (the content-script half of the gate worked, so the row toggled a setting with no visible effect). `popup.html` now carries an explicit `[hidden] { display: none !important; }`. Any new element you hide with the attribute must not carry a `display` rule of its own.

**Popup layout (v1.21.0)** — it must stay SHORT: Chrome caps a popup at 600px and the old one was ~1200px tall (the last rows were unreachable). 300px wide, 43px rows, 12px base font, and the two bulky editors (**menu items**, **reaction emoji**) are `<details>` **collapsed by default** — 434px closed, 677px fully open. Descriptions **wrap, never ellipsize** (a clipped privacy line is worse than an extra row). The menu list stays single-column because `popup.js`'s drag-reorder compares `clientY` only.

## Gotchas / invariants

- **What makes it feel heavy (audited 2026-08-14, NOT yet optimized)** — ranked, with live measurements in `docs/devlog/claude_2026-08-14-popup-compaction-observer-coverage-and-perf-audit.md`: (1) **PostHog**, mainly **session replay** — `vendor/posthog.js` is 543 KB parsed at `document_start` in *every* Basecamp document (**~18 ms** compile+exec) and rrweb then records/serializes/uploads the whole DOM continuously (`POST /s/` confirmed live) on every tab; (2) **we inflate the DOM ~25 %** (677 of 2985 elements on a 50-line ping room are ours — 8 emoji × 50 records = 400 buttons), which multiplies (1); (3) the **RTL pass** used to be our hottest path (`majorityDir` re-scanning every container's `textContent` *and* each block on every Turbo render) — **fixed in v1.21.0 by memoizing the vote**, see the gotcha below; what remains is ~1 ms of selector query per sweep; (4) one `/…/options` fetch + `DOMParser` per record; (5) `ccSyncBusy` every 10 s per tab keeps the MV3 service worker awake. Negligible: the 60 s label sweep (0.18 ms), `syncTheme` (0.04 ms), fonts (lazy, only the picked family). Fix order if we ever act: 1 → 2 → 3.
- **The CC button's mount point is re-resolved on every pass (v1.21.0).** Placement used to run only inside `if (!btn)`, so a button created before Turbo filled the composer stayed in the last-resort fallback (pane host) forever — seen live on a campfire, parked at the far left while `.chat__footer .chat__tools` existed. `applyCcLaunchers` now computes `home = tools || slot || pane.host` each pass and moves the button when `btn.parentElement !== home` (clearing `.bce-cc-beside` on the way out, since that class shrinks the input). Keep it that way; the DOM it mounts into arrives late.
- **A recurring `Uncaught TypeError: … 'classList'` on chat pages is BASECAMP'S bug, not ours** — `clearTypingStatus` in their `desktop-*.js`, every ~40 s on ActionCable connect, no extension frame in the stack. Their `RoomController` caches `statusElement = element.querySelector("[data-behavior~=chat_typing_status]")` **at construction**; where that node is missing (a disabled ping room has none) it stays null forever. Don't go hunting in our code for it — we never remove Basecamp nodes, only our own.
- **Idempotency is load-bearing** — the observer fires on our own badge insertions; the early-return + reuse-existing-badge logic is what prevents loops/duplicates. Don't break it.
- **`<time>` root case** — when adding `<time>` handling, remember `querySelectorAll("time")` matches descendants only. Bare-node decoration is a separate explicit check.
- **Revert must be exact** — RTL revert only touches `[data-bce-dir]`-tagged nodes, restoring the original value stored in the tag (`"none"`/legacy `"1"` ⇒ remove `dir`, else set it back); never blanket-strip `dir`, or you'd wipe Basecamp's own attributes. Keep `setDir`'s "only no-dir or `dir=auto`, never explicit `ltr`/`rtl`" invariant.
- **The direction vote is MEMOIZED — `force` is the invalidation, and only the observer may set it (v1.21.0).** `majorityDir` allocates the element's whole `textContent` and runs two regex scans, per container **and again per block**, so cost grew linearly with how much text a thread holds — on every Turbo render. `dirVote` (WeakMap, keyed by element) caches the vote; `decideDir(el, fallback, force)` recomputes only when `force` is set, which happens **only** on the mutation-driven path (`flushDirty` → `enhanceSubtree(el, true)`, `reDirContext` → `setAutoDir(c, true)`) — i.e. exactly "this element's text just changed". Every other pass reads the cache and **still verifies the `dir` attribute**, which must NOT be skipped: a Turbo morph syncs attributes from the incoming HTML and drops our `dir`/`data-bce-dir` while keeping the element (and its cache entry) alive. Measured on the real `content.js`: **13.31 ms → 0.97 ms** per `reconcile()` on a 477 K-char thread, 1.72 → 1.40 ms on a normal 26 K-char room; the point is that cost is now **flat in thread size**. Deliberate caveat: a cached block ignores `fallback`, so a block with zero strong characters keeps its inherited direction if its container later flips without the block's own text changing (the force path recomputes both together).
- **Don't add an IntersectionObserver to gate the RTL pass — measured, it can't help.** On a real room the pass splits as **0.985 ms for `querySelectorAll(RTL_SELECTORS)` itself vs 0.245 ms of per-element work** across all 76 matches, so gating adds per-target cost to save a fraction of the small half. The query is **~25–50 µs per selector per sweep** almost regardless of matches (`.formatted_content` 22 µs, `main h1` 32 µs, `[contenteditable='true']` 112 µs; all 26 ≈ 1.06 ms ≈ their sum) — so the v1.21.0 coverage additions cost **~+0.5 ms/sweep** (14→26 selectors). That's the knob if the sweep ever needs to get cheaper: fewer selectors, or sweep less often — not gating, and not a Worker (no DOM there; shipping text out costs what the scan costs).
- To support a new Basecamp view's RTL, add its content class to `RTL_SELECTORS`. **Titles/names/previews live OUTSIDE `.formatted_content`** and were never direction-decided until v1.21.0 — the card table was the worst case (a scan found 190 majority-Arabic elements computing `ltr`: every `.kanban-card__title`, the column titles, the page `h1`; project home added `.dock-card__title/__body`, `.vaultable-line__name/__summary-text`, `.recording-preview`, `.project-timeline-snapshot__content`). Chat/pings were already clean, so "RTL doesn't work" always meant a **board/list** view. `main h1,h2,h3` covers page + column headings generically; broad selectors are safe here because `majorityDir` returns `"auto"` for Latin-majority text, so English titles are untouched.
- **RTL chat composer clips its first words under the tool icons (`styles.css`, v1.12.8).** Basecamp's chat composer is a **lexxy editor** (`.chat__footer … lexxy-editor.formatted_content > .lexxy-editor__content`), and it already wraps typed text in its own `<p dir="auto">` — so Arabic goes RTL natively (our `dir=auto` on the container is redundant for the composer; the clip is not caused by our attribute). The composer's tool row (`.chat__tools`: emoji/attach/mic/format **+ our added `.bce-cc-btn`**) floats over the input's right edge; Basecamp reserves `padding-right:140px` for it, but **our CC button widens the row to ~165px**, so the reserved gap no longer clears the icons. In LTR that overlap is at the far, rarely-reached end of a line; in **RTL the text *start* aligns to that right edge**, so the first words tuck under the icons and read as "hidden" (verified live: text-start x jumped from **1149 → under tools.left 1125**). Fix is one CSS rule — `.main-content .chat__footer .lexxy-editor__content:has(p:dir(rtl)) { padding-right:172px !important }` — the `:has(p:dir(rtl))` gates it to composers that actually hold RTL text (an empty/LTR composer keeps Basecamp's 140px), and 172px clears the whole tool row **at any width** (the row is right-anchored + fixed-width, so `content.right − tools.left ≈ 164px` is width-independent). **The `.main-content` scope is load-bearing (v1.12.9)**: the **sidebar ping** composer (`.sidebar__frame` / `.sidebar__chat`, NOT under `.main-content`) puts its tools in a row **below** the input — Basecamp gives it `padding-right:10px`, no overlap — so the blanket v1.12.8 selector shoved that RTL text 172px off the right edge into the middle (the exact bug the user reported). Same page can show **both** composers at once (main + open sidebar ping); the two differ only by that ancestor. Verified visually with `/chrome`: main clears the icons, sidebar hugs the right edge. See [[always-visual-test-chrome]].
- **Flicker fix (was: time labels "appear and reappear")** — Basecamp streams updates over a `turbo-cable-stream-source` (WebSocket). A stream/morph render strips our badge/bar from *inside* an element that stays in place; a **removal** is not an added node or a text change, so the observer (even post-v1.21.0, which added `characterData`) never re-adds them — they'd vanish until the 60 s interval. The `turbo:*` listeners (which rAF-coalesce a `reconcile()`) are what restore them on the next frame. Don't remove them; the observer alone is insufficient.
- **Reactions post via the boost gid, not the DOM** — `sendBoost` derives everything (endpoint + gid) from the `.boosts__new-boost` href; it does **not** click Basecamp's UI. The CSRF token comes from `meta[name=csrf-token]` (works for all forms — no need to GET `/boosts/new`). If Basecamp changes the boost URL shape or gid encoding, update `boostTarget()` only.
- **`window.Turbo` is INVISIBLE to us — apply Turbo responses by hand.** Content scripts run in an **isolated world** with their own `window`; Basecamp's `window.Turbo` lives in the page's **main world**, so it's `undefined` in `content.js`. The boost-create reply is a **mixed** document — a `<turbo-frame id="boosts_recording_…">` (the refreshed reaction row) **plus** a `<turbo-stream action="update" target="new_boost_recording_…">` (the "+" button). The old `applyBoostResponse` saw the `<turbo-stream>`, called `window.Turbo.renderStreamMessage` — which was `undefined` — and silently no-op'd, so **the reaction only appeared after a page reload** (the POST itself succeeded; verified live). Fix (v1.13.x): `applyBoostResponse` parses the reply and does it with plain DOM — replace each `turbo-frame[id]` in place, then run each `<turbo-stream>` through a tiny `applyTurboStream` (append/prepend/before/after/update/replace/remove vs `target`/`targets`). Plain DOM crosses the isolation boundary fine, and a turbo-frame's light-DOM children render whether or not the custom element upgrades. **Never reach for `window.Turbo`/`renderStreamMessage` from the content script** — apply streams manually. (There's no per-emoji native button to "click" instead; our POST + manual apply *is* acting on Basecamp's real response.)
- **Hover menu = reused DOM, not reimplemented actions** — we clone Basecamp's real menu and rely on **Stimulus reconnecting** to the cloned/ancestor controllers; never reimplement Edit/Reply/Bookmark/etc. by hand. Two things make it render as a flat inline strip inside the pill: (1) `.action-sheet__content` ships **collapsed** (`opacity:0`, `position:absolute`, full-width block `.action-sheet__action` rows) — `styles.css` force-overrides (scoped under `.bce-hoverbar`) to a visible, static inline strip (those `!important`s are load-bearing) — and both `.bce-menu` and `.bce-reactions` are `display: contents` **inside the bar** so every emoji/menu item is a direct flex item of the wrapping bar (as inline-flex each wrapper was one unbreakable block that spilled out of narrow bubble-width pills; `.bce-reactions` stays inline-flex in standalone `.boosts`); (2) the popup-positioning `orientation`/`horizontal-offset` controllers live on the **un-cloned parent sheet**, so the lifted content isn't repositioned (we also strip its `data-*-target`/`style`). A relocated action works only because its controller is either a live ancestor (`chat--room`) or inside the clone (`copy-to-clipboard`/`bookmarks`) — verify both when Basecamp restructures. `copy-to-clipboard` uses `execCommand('copy')`, so it needs real user focus (won't fire from a headless click — the `copy-to-clipboard--supported` class confirms it *connected*).
- **Hover-bar positioning** — two modes, both `position:absolute` against `.bce-anchor`, revealed via `[data-bce-rec]:hover .bce-hoverbar` (descendant, since the bar is nested in the anchor, not a direct child of the record). **Reveal is JS-managed, not `:hover`**: content.js sets `.bce-open` on exactly ONE bar per document-level `mouseover` (`setOpenRec`) — pure `:hover` sometimes stuck (stream re-renders under the pointer swallow `mouseleave`) and couldn't guarantee a single open bar; any stuck state self-heals on the next pointer move. **The trigger is the `.bce-anchor` (bubble for chat, record for comments), NOT `[data-bce-rec]`**: a chat-line turbo-frame spans the full row width, so keying off it opened the bar whenever the pointer sat at the bubble's Y even out in the empty margin. `mouseover` does `t.closest(".bce-anchor")?.closest("[data-bce-rec]")`; since the bar is a descendant of the anchor (and overlaps above the bubble), hovering the bar still resolves to the anchor and stays open. `RECORD_SEL` excludes `.thread-entry--form` (the comment composer is a `thread-entry.recording` too — a draft must never grow bars; `applyHoverBars` also strips bars from anything tagged that no longer matches). **Menu prefs**: `applyMenuPrefs` matches each lifted item (prefix of its first `.action-sheet__action` text, lowercased) against `settings.menuItems`, hides via `data-bce-hidden` (attribute — inline `display` loses to our `!important` rules) and orders via flex `order` (works because the wrappers are the bar's flex items); it also sets each action's `title` (the clean `menuItems` label) — because menu items render **icon-only** (CSS `font-size:0` on `.bce-menu .action-sheet__action` collapses the bare-text labels, svg forced to 16px) to save space, the tooltip is the only label. Bubble-up sub-menu presets are exempt (`.action-sheet__content .action-sheet__action` restores text — you must read "Now"/"Tomorrow"). **Chat** (`[data-mine]` present): `left:0; right:0` (⇒ **bubble width**) + `bottom: calc(100% - 9px)` (**overlaps the bubble's own top edge — the overlap is load-bearing**: with any dead gap, the pointer lands on the record ABOVE mid-transit, that record steals `:hover`, and the bars flip; since the bar is a descendant, bubble→bar must be one continuous hover surface. The bar's `z-index:30` also makes hit-tests over its top rows — physically inside the upper record's box — resolve to the bar's own record, verified via `elementFromPoint`) + `flex-wrap:wrap`. Matching the bubble width is what fixes the received-message overflow — a bar pinned to a left-aligned bubble's *right* edge and grown leftward would run off-screen; bounding it to the bubble makes that impossible. **Comments** (no `[data-mine]`): a compact `top:0; right:0; translateY(-50%)` pill (already straddles its own record's edge ⇒ continuous). **Bubble-up sub-menu — the closed state must be `display:none` and it is OURS**: the sub-sheet ships in the clone collapsed, but Basecamp's hiding does not survive our `display … !important` overrides — v1.9.0 left the schedule presets as **invisible-but-clickable** boxes under the pill (opacity 0, boxes forced by our rules): clicking "empty" space could bubble the message up. So `styles.css` keeps `.action-sheet__content` at `display:none` and **opens on `.action-sheet--bubble-up:hover` OR `.bce-sub-open`** (v1.12.3 — same rule, comma-joined; the `> .action-sheet__content` is a descendant of the hovered sheet so there's no dead gap, and hover only fires while the bar is `.bce-open` = `pointer-events:auto`). `.bce-sub-open` (the pin) is still toggled by content.js's capturing click listener around Basecamp's own Stimulus handling; preset click or any outside click collapses it; `setOpenRec` collapses on bar switch. When open: contained block popup, full-width option rows, forced `opacity/visibility/pointer-events` (so we don't depend on Basecamp's open-state class). `details:not([open]) > *:not(summary) { display:none }` (scoped) restores native `<details>` hiding for the "Pick a date" pane. **The sub-sheet is a SECOND lazy `turbo-frame.action-sheet__lazy-options[src]`** (`/recordings/<id>/bubble_up/edit`) — empty in our clone, so pre-v1.12.3 opening it showed a **big blank box**. `loadBubbleUp(sheet)` fetches that frame (once, lazily, on first `mouseover` of the sheet) and `replaceChildren`s the presets in — reused DOM again (the loaded preset buttons submit through Basecamp's Turbo). **The preset icons need an EXPLICIT size** (`.action-sheet__content .action-sheet__action svg { width:18px }`) — v1.12.3 set them `width:auto` (to dodge the icon-only-menu's 16px shrink), but `auto` on these dimensionless SVGs balloons to the **300×150 intrinsic default**, rendering as giant wavy strokes filling the popup (v1.12.4 fix; verified visually with `/chrome`, not just DOM — see [[always-visual-test-chrome]]). **The sub-sheet stays `position:absolute` (CSS `top:100%`), horizontally clamped by `positionSubMenu(sheet)`** — a right-anchored popup spilled off the **left** edge in a narrow **sidebar ping** panel (v1.12.6). `positionSubMenu` sets only `left`, as a **sheet-relative offset**: `left = clamp(button.right − w, 8, innerWidth − w − 8) − sheet.left` (subtracting the sheet's own viewport-left converts the desired viewport-x into an offset). Right-aligned to the button when there's room, shifted inward when a narrow panel would push it off-screen. **Do NOT use `position:fixed` here** (v1.12.6's first attempt did, and it broke comments): a `fixed` element whose ancestor has a `transform` is positioned against that *transformed ancestor*, not the viewport — the **comment pill's `translateY(-50%)`** made the fixed popup anchor to the pill and fly off-screen (chat bars have no transform, so it "worked" there and the bug looked comment-only). `absolute` is immune — it's relative to the positioned sheet, and `getBoundingClientRect` already bakes in ancestor transforms, so the offset math stays correct. Called on hover (in `mouseover`, again after async `loadBubbleUp` resolves so width is final) and on the pinning click. Verified visually with `/chrome` on **both** chat (narrow + wide, mine/received) **and comments** — popup on-screen, directly below the button, zero overflow. `.action-sheet__action--info` rows (e.g. "The window to edit… closed") are dropped at build time. **Never let an opacity-hidden clone keep forced display — audit any new `display !important` against collapsed Basecamp UI.** Keep the toolbar **opaque + full-color** (the user explicitly asked for not-gray): `.bce-react-btn`/`.action-sheet__action` at `opacity:1`, no `grayscale()`; concrete hex + the `.bce-dark` runtime palette (see theming gotcha).
- **All HQ traffic goes through `background.js` — keep it that way.** Content scripts are CORS-bound to the page origin, so they cannot fetch `http://127.0.0.1:8377`; the service worker can because of `host_permissions` (`127.0.0.1:8377` + `localhost:8377`). **Do NOT "fix" this by adding CORS to the HQ server** — HQ has no auth, and CORS-opening it would let any web origin spawn permission-skipping Claude workers. The extension-only path IS the security boundary. Same reason: never feed page-scraped Basecamp text into the spawn prompt (prompt-injection into an unattended `--dangerously-skip-permissions` agent); only the user's typed text + the page URL.
- **The backend's `/api/workers` is a polling hot path — keep it cheap (fixed 2026-08-03, cc-tmux-api 0.2.1).** Several 5 s pollers (each open popover's `pollTray`, `ccSyncBusy` per tab, the HQ dashboard) once multiplied into ~100 tmux subprocess calls per GET (~8 per worker + per-routine `list-sessions` in HQ); the serial tmux server backed up until commands hit their 10 s timeout — intermittent 500s, gray tray dots, session names never getting their claude.ai href, and **spawns hanging >30 s in the same queue** ("Spawning worker…" stuck while the worker actually launched). cc-tmux-api now batches listing into ~2 tmux calls + one capture per worker behind a 2 s TTL cache (stale-served on a tmux stall, invalidated on spawn/kill). If those symptoms return, suspect a new per-worker/per-request tmux call before blaming the extension.
- **HQ spawn 200 ≠ launched.** `workers.spawn` types `claude` into a surviving shell, so the HTTP response can't see claude fail (bad flag, login error). Detect via the post-spawn poll (`ccConfirmLaunch`): status `working`/`waiting`/`idle` = up (**idle counts** — fast workers pass `working` between polls); `done` past the ~8 s grace = the pane fell back to a shell = failed (surface `tail`). A bad `workdir` does NOT fail: tmux silently falls back to another cwd (verified) — hence the extension sends none and the backend's default must be a known-good path.
- **Kill test workers.** Any `hq-*` session spawned while testing this feature is a REAL unattended Claude session — kill it when done (`POST /api/workers/action {action:"kill",session}`), same etiquette as deleting test boosts.
- **Overlay theming has TWO failure modes; the fix is runtime luminance detection.** (1) Dark Reader rewrites concrete hex but NOT system color keywords — `background: Canvas` stayed white while page text went light. (2) Basecamp's **native dark theme** doesn't touch our hardcoded `#fff` pill but its own (moved) menu items keep their light text → light-on-white. So: overlays use plain hex, and `syncTheme()` (called from `reconcile()`) samples the page's real background luminance — which reflects *whatever* darkened it (Basecamp theme, Dark Reader, anything) — and toggles `.bce-dark` on `<html>`, selecting the dark palette at the end of `styles.css`. Don't replace this with `prefers-color-scheme` (neither Basecamp's toggle nor Dark Reader flips it) or with Canvas keywords.
- **Pane-host assumptions — verified live on a sidebar ping (2026-07-22)**: a sidebar ping window does wrap its own `.chat__lines` with a stable non-scrolling `parentElement`, and its enclosing `turbo-frame[src]` gives the URL — as `/<acct>/my/sidebar/circles/<id>`, which 302s to the canonical `/circles/<id>`; `ccPaneUrl` strips the `/my/sidebar/` segment so workers get the canonical URL directly. Main + sidebar buttons coexist with independent URLs. Re-verify if Basecamp restructures; fix `ccPanes()`/`ccPaneUrl()` first.
- **`meId()` must stay a lazy lookup.** We run at `document_start`, when `<head>` doesn't exist yet — capturing `meta[name=current-person-id]` in a top-level const pins it to null forever, which silently killed `data-mine` (chat hover bars fell back to the comment-pill position) in the real extension, while injected-replica tests (which run post-load) passed. Query the meta at use time; beware the same trap for any other `document_start`-time DOM capture.
- **Orphaned-content-script guard (`ctxAlive`).** After the unpacked extension is reloaded/updated, the old `content.js` still runs in already-open tabs but its context is gone — every `chrome.*` call then throws **"Extension context invalidated"** (`chrome.runtime.sendMessage` throws *synchronously*, so a `.catch` alone doesn't swallow it). Our observer + intervals kept calling chrome and spammed the console (with a bogus line number, mapped against the *old* build — the string at `content.js:569` can't throw). Fix: `ctxAlive()` (`!!chrome.runtime?.id`, in a try/catch) gates every chrome call — `hqSend` (try/catch for the sync throw), `saveCcSessions` — and the `MutationObserver` (highest-frequency callback) calls `teardown()` on the first dead tick to `disconnect()` + clear all three intervals (`labelTimer`/`ccBusyTimer`/`ccPollTimer`), so the orphaned page goes fully quiet. A tab refresh loads the fresh script. Not a bug the user can hit at runtime — only after a manual reload — but keep the guard so dev reloads stay clean.

## Packaging / publishing

- Icons: `icon.png` (512², source of truth) = the Basecamp logo-mark with the orange Basecamp app-icon composited as a rounded badge (soft shadow) in the bottom-right. Downscale to the four sizes with `for s in 16 32 48 128; do magick icon.png -filter Lanczos -resize ${s}x${s} -strip icons/icon$s.png; done`. Re-run after editing `icon.png`.
- **`./scripts/build.sh` is the ONLY way to build the upload zip** (`--check` validates without zipping). It parses every JS file, runs `tests/*_test.mjs`, enforces the store's two hard manifest limits (**name ≤ 45, description ≤ 132 chars** — ours was **180** for eight releases, which the upload rejects), asserts every manifest-referenced path exists, then writes `dist/basecamp-enhancer-<version>.zip` (runtime files only, manifest at root; `README.md`/`CLAUDE.md`/`icon.png`/`docs`/`tests`/`scripts` excluded) and verifies the manifest really is at the zip root.
